# Modo paralelo assistido

Lido pelo `lead` quando o `sessions.sh` avisar de outras atividades, quando a sessão estiver numa worktree de atividade e antes de propor abrir uma.

Os scripts aparecem como `<plugin>/scripts/<nome>`: `<plugin>` é a pasta do plugin que o núcleo da skill dá na seção Scripts do plugin (o Read não troca variável neste arquivo). Chamar pelo caminho inteiro, como o núcleo manda.

Várias atividades ao mesmo tempo, uma sessão por atividade, cada uma na própria worktree, com o desenvolvedor presente supervisionando. O paralelismo é entre atividades: dentro de cada uma, plano, sprints em ordem, subagentes, revisão e gates seguem como sempre.

- **Uma sessão por atividade, numa worktree própria.** O desenvolvedor abre a atividade com `<plugin>/scripts/nova-atividade.sh <nome>` (branch `task/<nome>`, worktree em `.claude/worktrees/<nome>`, runtime isolado) ou com `claude -w <nome>`, que cria a worktree sozinho (sem o slot de runtime, que o `lead` reserva no Início). Nunca reaproveitar a sessão de uma atividade encerrada para começar outra: o contexto anterior contamina o plano, e base do diff, contador de iterações e registro misturam as duas. Com `worktree.baseRef: "head"`, o `claude -w` cria a worktree a partir do HEAD de quem o roda: abrir a atividade a partir de um checkout na `main` (ou com `<plugin>/scripts/nova-atividade.sh <nome> --base origin/main`); no Início de uma atividade nova, `git log --oneline origin/main..HEAD` precisa vir vazio, senão parar e avisar o desenvolvedor (ela herdaria commits de outra atividade).
- **Runtime isolado.** Subir a aplicação, o banco e os containers só com as variáveis de `.claude/worktree.env` (faixa de portas, sufixo do banco, projeto do Compose), nunca com as portas fixas de desenvolvimento do AppHost.
- **Declarar o que o plano vai tocar.** Ao fechar o plano, `<plugin>/scripts/sessions.sh claim <arquivos e pastas previstos>` e `<plugin>/scripts/sessions.sh check`. Sobreposição com outra atividade ativa vai no plano: reduzir o escopo, esperar a outra terminar, ou o desenvolvedor decide a ordem. Atualizar o `claim` se o plano mudar.
- **Perguntas no plano.** Juntar todas as dúvidas na apresentação do plano, para a aprovação única resolver; o que um experimento decide, decidir por experimento (seção Aprovação única do núcleo). Uma sessão parada esperando resposta enquanto o desenvolvedor olha outra é tempo perdido.
- **Entrega por PR.** O plano diz explicitamente que a entrega é push da branch e abertura de PR, para a aprovação cobrir isso. Antes do PR: rebase na base, gates de novo e descrição no formato da skill `commit` (Pull request). Rotular o PR com o nível final do `classify-diff.sh` (`gh pr edit <n> --add-label risco:<nível>`): é o que a Action `merge-por-risco` usa para exigir revisores. O `lead` nunca faz merge (`gh pr merge` é `deny`); o merge é do desenvolvedor, na ordem que ele escolher, ou da Action quando o PR é só documentação TRIVIAL e o repositório tem proteção de branch; quem fica para trás faz rebase. Sem proteção de branch no repositório, o check de risco é só informativo e o merge é sempre manual.
- **CRITICA fora do paralelo no começo.** Atividade CRITICA pede atenção inteira do desenvolvedor; até um experimento mostrar o contrário, ela roda sozinha.
- **Ao terminar.** Não remover a própria worktree nem a branch: são a casa da atividade até o merge; depois do merge, a branch local sai pelo `prune-merged.sh` (`limpeza.md`, Branch mesclada).
